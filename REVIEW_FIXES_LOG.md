### Примечание о редакторских ошибках типизации (ложные срабатывания)

Pylance/Pyright в VS Code может показывать на `IMPORT_SPECS` в `load_csv.py` ошибки вида «objects is not present» с развёрткой `Literal[...]`. Причина: атрибут `objects` у Django-моделей создаётся метаклассом `ModelBase` в рантайме, а статически его объявляет только mypy-плагин django-stubs (строка `plugins` в `mypy.ini`). Pyright архитектурно не умеет исполнять mypy-плагины, поэтому не видит атрибут и рушит всю цепочку присваивания. Контроль типов в проекте — строго через CLI: `python -m mypy` (с плагином), ruff, flake8, pytest; все четыре зелёные (см. раздел 12).

## 13. Отказоустойчивость регистрации (транзакции, ретраи, кастомные исключения)

- Транзакция в `signup_user` (`users/services.py`): `get_or_create` и `save(update_fields)` раньше были двумя отдельными авто-коммитами (`ATOMIC_REQUESTS` в проекте не включён); сбой UPDATE оставлял бы в БД пользователя без кода подтверждения. Теперь обе операции под `transaction.atomic` — сбой записи кода откатывает и создание.
- `send_mail` остался **снаружи** транзакции (антипаттерн «почта внутри atomic»: медленный SMTP держит блокировки БД). Отказ доставки не откатывает создание: повторный signup регенерирует и высылает код заново — задокументированное поведение.
- Ретраи доставки (`users/services.py`): до `EMAIL_MAX_ATTEMPTS=3` попыток с экспоненциальной задержкой (`EMAIL_RETRY_BACKOFF=0.2`: 0.2/0.4/0.8 c). Ловим узко: `ConnectionError` и `OSError` — последний покрывает `smtplib.SMTPException` (наследуется от `OSError`). Каждая неудача — `logger.warning`; после исчерпания — `EmailDeliveryError` с исходной ошибкой в `__cause__`. Цикл вместо декоратора `@retry`: generic-механизм ради одного места — тот же принцип, что «класс ради функции не нужен».
- `users/exceptions.py`: `EmailDeliveryError` — ожидаемое исключение доставки (email + attempts, `__cause__`-цепочка), по образцу `reviews/management/exceptions.py`.
- Вьюха signup: `EmailDeliveryError` ловится и отвечает `SERVICE_UNAVAILABLE` с понятным сообщением — отказ внешнего сервиса (SMTP) теперь честный 503, а не сырой 500.
- `load_csv` сознательно **без** транзакций/ретраев: одна atomic на файл противоречит семантике «плохая строка пропускается с warning» (исключение внутри atomic ломает транзакцию целиком), per-row atomic — сотни мелких транзакций без выгоды. Реальная гарантия целостности импорта — идемпотентность `update_or_create`: перезапуск команды доводит БД до консистентного состояния, что надёжнее отката.

## 15. Второй раунд ревью: защита окружения, гонки регистрации, импорт

- **Валидатор окружения усилен** (`settings.py`): пустой/пробельный `SECRET_KEY` отклоняется явно; вне DEBUG требуется длина не менее 50 символов (`MIN_SECRET_KEY_LENGTH`) — угадываемый «вручную придуманный» ключ позволял подделывать подписанные им JWT; `ALLOWED_HOSTS` при `DEBUG=False` обязан быть непустым списком конкретных хостов (пустое значение делало API недоступным для любого Host).
- **Чистый клон снова рабочий** (`manage.py`): команды первоначальной настройки (`migrate`, `makemigrations`, `load_csv`, `collectstatic`, `createsuperuser`, `shell` и др. — набор `SETUP_COMMANDS`) больше не требуют переменных окружения, документированный сценарий «клон → venv → migrate» выполняется. Прод-точки входа (`runserver`, `wsgi.py`, `asgi.py`) валидацию проходят как раньше. В README добавлен шаг `set DEBUG=true` перед `runserver` с пояснением.
- **Гонки параллельных регистраций** (`users/services.py`): `get_or_create` сам разрешает гонку создания по username; гонка уникального email у разных username ловится (`IntegrityError`) и превращается в DRF `ValidationError` (400) вместо сырого 500; существующий аккаунт с чужим email (создан между проверкой сериализатора и запросом) не используется — `ValidationError`, код не уходит на чужой адрес.
- **Хэш и письмо согласованы**: доставка перенесена внутрь `atomic` под `select_for_update` строки пользователя — параллельный signup не может перезаписать хэш между сохранением и доставкой, полученный по почте код всегда совпадает с сохранённым. Компромисс осознанный: «SMTP внутри транзакции» раньше считали антипаттерном, но корректность кода подтверждения важнее, а цена блокировки ограничена тремя ретраями. Сбой доставки теперь откатывает и создание аккаунта (повторный signup создаст заново) — поведение задокументировано в докстринге.
- **`smtplib.SMTPException` явно в ретраях** (`_RETRYABLE_MAIL_ERRORS`): наследуется от `OSError`, но назван явно — при изменении иерархии исключений stdlib ретраи не потеряются.
- **`load_csv`: битая строка связок не останавливает импорт**: `_import_genre_titles` ловит ошибку каждой строки (нет колонки, битое значение, битый FK), печатает предупреждение и продолжает — поведение унифицировано с `_import_csv`.
- **`validate_year()` получил нижнюю границу** `MIN_YEAR = -32768` (минимум `SmallIntegerField` поля `year`): непредставимое для БД значение отсекается валидатором, а не падает на уровне БД. Сам тип поля **не откатывали**: `SmallIntegerField` требует предыдущее ревью (#52), данные CSV (1739..2012) покрывает с запасом — новое замечание противоречило старому.
- **Отклонено замечание про `EMAIL_BACKEND`**: консольный бэкенд зафиксирован осознанно — учебный проект, письмо с кодом печатается в консоль, из него берётся `confirmation_code`; продовый SMTP-бэкенд вне объёма ТЗ.
- **Тесты изолированы и расширены**: параметризация валидатора задаёт безопасные значения остальным настройкам (иначе ошибки маскируют друг друга — проверка падала на первом же параметре); новые кейсы: пустой/пробельный/короткий `SECRET_KEY`, пустой `ALLOWED_HOSTS`; сервисные: письмо уходит внутри atomic-блока (проверка `in_atomic_block` в моке отправки), конфликт email → `ValidationError`, `SMTPException` ретраится; новая группа `_import_genre_titles` — битые строки пропускаются с предупреждением, валидная импортируется.
