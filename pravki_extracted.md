### #10 [Надо исправить] файл: commands/load_csv.py

В try обычно помещают как можно более короткие блоки кода, чтобы ловить исключения как можно более прицельно.
- https://pep8.org/#programming-recommendations
- https://wemake-python-styleguide.readthedocs.io/en/latest/pages/usage/violations/complexity.html#wemake_python_styleguide.violations.complexity.TooLongTryBodyViolation
Additionally, for all try/except clauses, limit the try clause to the absolute minimum amount of code necessary.
Again, this avoids masking bugs.
Почти никогда нет смысла включать в блок try:
- проверки ошибок,
- вложенные конструкты try/except
- и возврат из функции.
Особенно если проверки выбрасывают исключение в случае ошибки.
Давай выносить подобное за пределы блоков try/except.

### #18 [Надо исправить] файл: migrations/models.py

Любому обобщенному решению для повторяющихся фрагментов запросов к БД
не место ни в моделях (models.py), ни во вью (views.py), ни в mixins.py - и т.д.
Функции добавления фрагмента или классы запросов (наследники QuerySet)
обычно отселяют в querysets.py (или аналоги),
потому что они про запросы к БД.
Менеджеры моделей (model managers) - это уже не совсем модели все же.
Обычно их отселяют в managers.py или querysets.py, например.

### #26 [Надо исправить] файл: migrations/serializers.py

Это откат: раньше код был лучше в этом отношении, и для текущей правки не было поводов.
Теперь лучше хотя бы вернуть, как было.
Сериализаторы - часть слоя АПИ. Они должны быть где-то среди пакетов (package), вложенных в пакет api.
Другое дело, что serializers - не обязан быть одним огромным модулем (module).
Его как раз бывает удобно сделать пакетом и разбить на несколько более мелких модулей.
Упрощенно: давай вынесем все модули про DRF в джанго-приложение api, как это было в прошлых домашках.
Чаще всего это: filters, pagination, permissions, serializers, views (только апишные) .
Также маршруты (URL patterns), относящиеся к API, должны быть в модуле urls этого джанго-приложения api.
Сейчас вся эта функциональность получилось несколько "размазанной" по другим джанго-приложениям.
В во всех ДЗ с DRF джанго-приложение api вынесено отдельно не просто так.
Дело в том, что REST API - это только один из способов вызова нашей программы.
На это в том числе указывает буква I в "API", она означает "интерфейс", т.е. "способ взаимодействия".
Альтернативой может быть, например, интерфейс командной строки (CLI):
т.е. мы можем написать консольную утилиту для работы с той же самой структурой данных.
Поэтому такие способы доступа лучше отселять отдельно, в специальный пакет.
В случае "Джанго" обычно это джанго-приложение api с пакетами для разных версий АПИ внутри.

### #8 [Можно лучше] файл: commands/load_csv.py

Для неизменяемых словареобразных объектов на входе можно использовать интерфейс Mapping,
для изменяемых - MutableMapping.
- https://docs.python.org/3/library/typing.html#typing.Mapping
- https://docs.python.org/3/library/typing.html#typing.MutableMapping
Это сделает диапазон допустимых типов данных на входе шире,
что обычно желательно для внешних интерфейсов (public interfaces).
Чтобы это лучше понять, можно познакомиться с (неуниверсальным) принципом из языка "Го":
"принимайте интерфейсы, возвращайте (конкретные) структуры (данных)".
A great rule of thumb for Go is accept interfaces, return structs. (Jack Lindamood)
Здесь важно учесть, что интерфейсы в "Го" объявляет вызываемая сторона, а не вызывающая.
В "Пайтоне" такой вариант интерфейса называется "протокол":
https://peps.python.org/pep-0544/
Иногда их еще называют "неявные интерфейсы" (implicit interfaces).
Дополнительное чтение:

- https://bryanftan.medium.com/accept-interfaces-return-structs-in-go-d4cab29a301b

Можно лучше
Для неизменяемых словареобразных объектов на входе можно использовать интерфейс Mapping,
для изменяемых - MutableMapping.
- https://docs.python.org/3/library/typing.html#typing.Mapping
- https://docs.python.org/3/library/typing.html#typing.MutableMapping
Это сделает диапазон допустимых типов данных на входе шире,
что обычно желательно для внешних интерфейсов (public interfaces).
Чтобы это лучше понять, можно познакомиться с (неуниверсальным) принципом из языка "Го":
"принимайте интерфейсы, возвращайте (конкретные) структуры (данных)".
A great rule of thumb for Go is accept interfaces, return structs. (Jack Lindamood)
Здесь важно учесть, что интерфейсы в "Го" объявляет вызываемая сторона, а не вызывающая.
В "Пайтоне" такой вариант интерфейса называется "протокол":
https://peps.python.org/pep-0544/
Иногда их еще называют "неявные интерфейсы" (implicit interfaces).
Дополнительное чтение:
- https://medium.com/@cep21/what-accept-interfaces-return-structs-means-in-go-2fe879e25ee8
- https://bryanftan.medium.com/accept-interfaces-return-structs-in-go-d4cab29a301b
- https://dev.to/lcaparelli/should-my-methods-return-structs-or-interfaces-in-go-3b7
